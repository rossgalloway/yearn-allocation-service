# Allocation history reference-spec deltas

Reference: [Vault Allocation History — Spec](https://hackmd.io/@murderteeth/rJkQlX-AWx)

This document records deliberate prototype differences, clarifications discovered through live data, and unresolved schema
questions. Update it whenever behavior diverges from the reference so the Kong implementation can either adopt or reject the
change explicitly.

## Accepted prototype changes

| Area | Reference spec | Prototype behavior | Reason / future action |
| --- | --- | --- | --- |
| Snapshot pairing | One block-end state per relevant event block. The preceding event state is the transition's `fromStateId`. | Every returned event transition at block `N` references an immediate pre-state read at `N - 1` and a post-state read at `N`. Both states are returned and adjacent blocks are deduplicated. | Captures the actual before/after allocation change even when deposits, withdrawals, or other non-allocation activity occurred since the previous allocation event. Kong should preserve this pairing. |
| Response order | States and transitions are chronological (oldest first). | `direction=desc` is the default so clients walk backward from current state. `direction=asc` restores chronological order, and the response echoes the selected `direction`. Link semantics remain chronological: `fromStateId` is always before and `toStateId` is always after. | Better default for current-to-history exploration while retaining chart-friendly ascending output. |
| Strategy status | Directory status is current, but the source is not prescribed. | Current status comes from the latest safe-block RPC `strategies(address).activation` value. Envio lifecycle events define the historical universe, not current status. | Live data established that `StrategyChanged` uses `1 = added`, `2 = revoked`; relying on a misread enum marked every strategy inactive. |
| DOA matching | Multiple signals may identify an execution, including keeper paths and debt direction. | A proposal becomes a confirmed policy only when indexed allocator configuration events exactly match its strategy targets. Historical RPC target equality can attach an explicitly inferred policy to an allocator entry. Keeper identity, direction, and timing never establish policy application by themselves. | The shared allocator's configuration event is not yet indexed by Envio. The API must expose that evidence gap rather than convert a likely execution into a confirmed policy. |
| DOA execution span | The schema annotates transitions but does not explicitly state whether one proposal can match more than one transition. | A policy revision persists until superseded and may annotate many separate REST entries. Each logical keeper run gets one whole-group before/after entry containing its transaction steps. | Separates policy application from later maintenance and prevents an indefinitely open proposal entry from swallowing unrelated future activity. |
| Vault activity context | `Deposit` and `Withdraw` are not in the required source-event list, and their associated `DebtUpdated` events fall into `manual_debt_update`. | Envio `Deposit` / `Withdraw` rows are fetched as context-only events. Pure withdrawal-servicing debt updates are omitted from public REST. When allocator, historical `DEBT_MANAGER`, bad-debt, configuration, or lifecycle evidence exists, the entry remains visible and retains exact assets, shares, participants, event ID, and direct/routed path under `vaultActivities`. Deposit-driven debt updates remain visible. | Live yvUSDC evidence showed that 83 of 85 nominally manual debt updates satisfied withdrawals. Treating withdrawal as intent would either flood the chart or conceal mixed emergency/admin actions; it is therefore an independent context axis. |
| Trusted keeper without proposal | Keeper-path debt changes without a matching DOA proposal are `manual_debt_update`. | A traced call through the active allocator sets `execution.mechanism = allocator_keeper` independently of policy. Historical `shouldUpdateDebt` replay sets the independent automation and target-status axes: a match is automatic/matched, a different target is manual/overridden, and unavailable replay remains unknown/unavailable. | Keeper identity proves neither DOA provenance nor that the keeper used the allocator's recommended target. |
| Materialized history | Production blobs contain rebuilt and incrementally maintained full history. | A background job fully pages Envio, performs archive-RPC enrichment, filters/groups public entries, and writes a certified immutable Postgres run. REST keyset-paginates those entries without upstream calls. The test-service `refresh` still rebuilds the complete run rather than updating an immutable prefix plus mutable tail. | Removes request-time history limits and makes public latency predictable. Kong should replace full-copy refreshes with an incremental tail algorithm before broad vault rollout. |
| Uncertified test materialization | The reference assumes its indexed inputs are available and does not define a degraded publication mode. | An explicit test-only flag may activate an immutable provisional database run from Envio events plus archive-RPC snapshots when coverage/checkpoint entities are missing or incomplete. Responses are uncached, expose run and entry limitations, and keep checkpoint-owned unallocated fields null. Certified-only remains the default. | Lets this non-production prototype exercise the complete database/REST shape against the currently available event index without disguising absent evidence. Kong should not inherit this exception as a production default. |
| REST cursor | The reference uses numeric offset/limit pagination. | `nextCursor` is an opaque versioned keyset cursor over `(endBlock,id)`. It pins the immutable materialization run, direction, and full/chart response projection selected on the first page. | Offset pagination can skip or duplicate entries when a refresh activates. Projection binding prevents a filtered chart cursor from traversing the full row set. Retained run IDs make a traversal stable, at the cost of requiring a cursor-expiry and run-retention policy. |
| Supported vaults | All Kong-supported V3 vaults and chains. | Ethereum-only: `yvUSDC-1`, `yvUSDT-1`, and `yvUSD`. | Explicit test scope requested for archive-RPC enrichment. |
| Public REST shape | The reference exposes normalized top-level strategy, state, and transition collections. | Schema version 2 exposes a denormalized `entries` timeline. Each entry embeds its whole-group before/after state, strategy changes, structured lifecycle/configuration operations, policy context, compact transaction steps, actor attribution, and classification evidence. Normalized objects are retained internally for a future investigative GraphQL surface. | Website hydration should render charts and transaction tooltips without follow-up requests. Repeated policy and strategy metadata is an intentional REST read-model tradeoff. |
| Compact chart projection | The reference defines one allocation-history response shape. | `projection=chart` filters to visible `strategy_reallocation` entries before pagination. It keeps raw after-state amounts, execution axes, proposal APR, and detail links; removes duplicate BPS, atomic before/start data, transactions, operations, and classification; deduplicates strategy names; and returns only `nextCursor`. Gzip is used when accepted. | The known chart consumer only renders strategy-reallocation panels. Hidden activity still belongs in interval accounting, while details remain available from the run-pinned entry route. |
| Interval flow ledger | The reference exposes event transitions and block-end states but does not define a reconciled ledger between public chart points. | Chart intervals now span directly between visible strategy reallocations; the safe-head tail has a null `toEntryId`. Raw-unit flows retain literal external transfers, accounting gain/loss, derived debt movement, and residual unattributed changes. Repeated interval states are replaced by entry references plus response-level `boundaryStates`. Successful residual equations and detailed totals move to the detail response. | Consecutive reallocations can differ because of deposits, withdrawals, reports, refunds, debt servicing, and other accounting changes. The API owns that accounting so the frontend only lays out evidence-qualified ribbons, while avoiding repeated boundary states and hidden-entry pagination. |
| Action taxonomy | The reference primarily classifies transitions by proposal/manual execution provenance. | Public `kind` describes the whole-group economic flow: increases without strategy decreases are `idle_deployment`, decreases without increases are `idle_deallocation`, and both directions are `strategy_reallocation`. `execution.automation`, `execution.mechanism`, and `execution.targetStatus` independently record automatic/manual choice, routing, and allocator-target matching. `policy` remains independently nullable. Exact lifecycle/configuration changes live in `operations`; only pure no-flow actions use lifecycle/configuration kinds. | The block-25584213 yvUSDC action deployed accumulated idle after separate deposits and was neither a new policy nor a strategy-to-strategy reallocation. Block 25404333 combines a manual Safe reallocation with a strategy retirement, so one provenance-oriented kind would discard useful information. |
| REST event scope | Every indexed state transition can appear in the response. | Standalone deposits/withdrawals, report-only changes, and pure withdrawal-servicing debt updates do not appear in default REST. A withdrawal-associated allocator, privileged-role, bad-debt, configuration, or lifecycle action remains visible. A `current_snapshot` preserves the latest chart state. | High-volume liquidity servicing should not displace meaningful allocation actions, but filtering on `Withdraw` alone could hide emergency or governance activity. Detailed vault-flow rows remain internal for future GraphQL. |
| Multi-transaction grouping | Transitions are block-scoped. | State-continuous allocator or manual steps may form one entry when they are adjacent allocation actions, share the same resolved execution path and historical allocator configuration, occur within one hour, and have exact historical trigger/role evidence. Time proximity is supporting evidence and is never sufficient by itself. | Models one logical keeper/manual run while failing closed when archive trace or trigger evidence is insufficient. |
| Allocator ratios | The reference does not distinguish vault-bound and shared allocator getter shapes. | Historical state calls the shared allocator's `getStrategyConfig(vault,strategy)` and decodes `added`, target, and max ratios. | The previous one-address target/max calls reverted against the shared allocator and silently produced null ratios. |
| DOA lifecycle | Proposals are labeled `pending`, `unmatched`, or `stale` using elapsed-time windows. | Public REST only embeds a proposal when its policy is relevant to an entry. An exact indexed configuration event produces `application.status = confirmed`; an exact historical target match produces `inferred_from_historical_config`. Internal unapplied proposals are `unmatched` or `superseded`; age alone never changes status. | Applied allocator targets persist until superseded. A 72-hour request expiry is not part of the allocator contract. |
| Actor attribution | `transactionFrom` supplies the transition actor. | Archive `trace_transaction` resolves the originator, transaction target, complete call path, and immediate vault caller. Historical Envio `RoleSet` masks determine whether that caller held `DEBT_MANAGER`; unavailable traces/role history remain explicit null evidence. | Relayers and Safe transactions make the top-level signer insufficient for distinguishing allocator and manual role execution. |
| Allocator trigger evidence | Trusted actor plus timing/direction can identify allocator execution. | For traced allocator calls, REST replays `shouldUpdateDebt(vault,strategy)` at block `N-1` and compares the returned target calldata with the executed `DebtUpdated.newDebt`. The response discloses the absolute difference and match tolerance; tolerance is the greater of 0.001 asset units or one-billionth of the executed debt. A larger mismatch sets `execution.automation = manual` and `execution.targetStatus = overridden`; a match sets automatic/matched, while before/after debts independently determine the economic-flow kind. | The allocator permits keepers to submit arbitrary target debt, while block-to-block profit unlocking can create sub-unit differences between the preceding block read and exact transaction pre-state. |
| Unallocated value provenance | State snapshots expose an unallocated ratio without a separate evidence reference. | REST sets `unallocatedBps` only when an exact same-block canonical Envio checkpoint agrees byte-for-byte with the archive-RPC totals. It also returns `unallocatedSource` and `unallocatedCheckpointId`; all three are null otherwise, including many `N-1` pre-snapshots. | Archive RPC can prove before/after totals, but the service contract gives Envio exclusive authority over the indexed unallocated value. Null is not zero. |
| Optimizer availability | DOA proposals are part of the history response construction. | DOA remains optional policy enrichment. A Redis outage does not block a certified executed-history refresh; affected entries disclose the missing proposal feed in `classification.limitations`. | Optimizer proposals are outside the executed-history authority boundary and must not make public on-chain history unavailable. |

## Clarifications retained from the reference

- Internally, states remain archive-RPC materializations and transitions remain derived from Envio events. REST embeds their
  consumer-relevant fields instead of exposing those normalized collections.
- The live tail is rendered as a self-contained `current_snapshot` REST entry with no claimed execution delta.
- DOA records annotate policy provenance but never create executed allocation state.
- Raw Envio events, intermediate snapshots, full traces, role history, grouping diagnostics, and unapplied proposal searches are
  reserved for a future Kong GraphQL capability. This prototype does not implement a GraphQL server.

## Open schema decisions

1. Define how `maxDebtBps` represents an unlimited `maxDebt == uint256.max`; the current numeric ratio is too large for exact
   JavaScript representation.
2. Provide keeper/applicator labels for chains beyond Ethereum and decide how address changes are governed. The Ethereum TKS
   keeper used by this prototype is `0x283132390ea87d6ecc20255b59ba94329ee17961`.
3. Add the shared allocator ABI variant that emits a vault-indexed ratio event to `yearn-envio`, replay it, and expose it through
   normalized `AllocationSourceEvent` rows. Until then, affected REST policies can only be
   `inferred_from_historical_config`, never `confirmed`.
4. Replace the test service's complete-copy refresh with an incremental immutable-prefix/mutable-tail algorithm, then define a
   cursor/detail-link lifetime and old-run retention policy. Until then, historical reclassification creates a new run and old
   runs remain queryable by already-issued cursors and chart detail links.
5. Define the Kong GraphQL schema and authorization/rate-limit policy for raw events, traces, intermediate states, role history,
   and grouping evidence. The normalized internal identifiers are intentionally not part of the public REST contract.
